# 学习通通知中心 · 只读抓取（2026-09-23 实测打通）

## 一句话结论

**完全不需要浏览器、不需要 headless、不需要走 SSO 跳转。**
把 cookie 直接挂到 `.chaoxing.com` 域，用标准库 `urllib` POST 一次就拿到 JSON。

> 一个常见误区：先去折腾「headless 注入父域 cookie」。
> **那条路本身就是绕远的**。cookie 不必「注入浏览器」，直接把域改对即可。

## 凭据来源

| 项 | 值 |
|---|---|
| cookie 文件 | `%APPDATA%\Tencent\Marvis\User\<uid>\workspace\conv_<会话id>\temp\xxt_cookies.txt` |
| 格式 | **单行 `name=value; name=value`**（19 条，**不是** Netscape 格式，别当 curl cookie jar 用） |
| 关键键 | `vc` / `vc2` / `vc3` / `_uid` / `UID` / `fid` / `website_id` / `44165userinfo` |

⚠️ **注意**：交接时若只写相对路径 `temp\xxt_cookies.txt`，换会话就找不到了 —— 记绝对路径。

⚠️ **会过期**。失效判据：`getNoticeList` 返回 `status=false`；页面 title 从「通知」变「用户登录」。届时需用户在浏览器重登一次学习通。

## 接口规格

### 列表（主用，只读）

```
POST https://notice.chaoxing.com/pc/notice/getNoticeList
Header:
  Content-Type: application/x-www-form-urlencoded
  X-Requested-With: XMLHttpRequest
  Referer: https://notice.chaoxing.com/pc/notice/spaceNotice
Body:
  spaceNotice=1&type=&notice_type=&lastValue=&folderUUID=&year=
```

**⚠️ 坑（实测）：六个参数必须全带，哪怕是空值。**
只传 `spaceNotice=1` → `{"status":false,"msg":"参数错误^_^"}`（32 字节）。
六参齐全 → `{"status":true,"notices":{"lastPage":0,"lastGetId":"…","list":[…]}}`（约 15 KB）。

### 未读红点（慎用）

```
GET /pc/notice/checkNoticeRedDot
```

⚠️ 它在源码里挂在「**清除红点按钮**」的 click 上 → **可能真的消费用户的未读状态**。
未确认只读前**别调**。

### 🔴 禁调（会改用户账号状态）

`clearNoticeRedDot` / `setNoticeUnread` / `delNoitce`

## 通知条目字段（实测 4 条，每条约 37–39 字段）

| 字段 | 用途 |
|---|---|
| `uuid` | **唯一 ID → 去重键**（形如 `$CACG$2c77ba05-…`） |
| `title` | 标题 |
| `content` | 正文（纯文本，含时间/地点/变更信息） |
| `sendTime` / `completeTime` | 发送 / 完成时间 |
| `isread` / `redDot` | 未读状态 |
| `sourceType` | 实测均为 `14` |
| `idCode` / `tag` / `top` | 辅助 |
| `attachment` / `imgs` | 附件、图片（部分通知有） |

## 增量检测

**记录已见 `uuid` 的集合，差集即新通知。**
不要依赖 `lastValue` 游标 —— 语义未验证。

## 三条硬约束（用户明示，2026-09-23）

1. **不弹窗 / 不占前台 / 不周期开浏览器** → 纯 HTTP 天然满足 ✅
2. **要能实时写入、修改日程**（不是只写「待处理标记」）
3. **三锚点绝对不可动**：`07:00 抢座` / `21:30 停屏` / `23:00 就寝`
   → 改真源前后**校验这三行指纹**，异常立即回滚 + 上报

## 推荐架构（配合守夜服务）

```
常驻脚本（纯 Python，零 token，分钟级）
  → getNoticeList → 比对已见 uuid → 新通知落 pending_notice.json
  → 关键词预筛（时间/地点/课程/停课/调课/作业）命中
      → 唤起一次 AI 会话判断「该不该改日程、怎么改」
          → 改真源（带三锚点校验）
              → 守夜秒级重放 → 手机更新
```

**为什么加「预筛」**：通知五花八门（教材、平台入班、会议号…），大多数不需要动日程。
预筛把 90%+ 的通知零成本跳过，只在真像「日程变更」时才花钱。

## 💰 token 成本（2026-09-23 实测，回答用户「会不会消耗我的 token」）

**会 —— 但只有 ③④ 两类才花，①② 是零。**

### 实测基线（Marvis 侧 `llm_token_usage` 表，22,880 行）

| 日期 | 调用次数 | total tokens |
|---|---|---|
| 2026-09-22 | 2,315 | **131,187,265** |

**单次 input 中位数 5.4 万、最高 9.1 万** —— 长会话每次都要重发整个历史。
**全新短会话的基线开销 ≈ 2.5 万 input**（system prompt + 工具 schema）。

> 「对话长了卡」与「烧 token」是**同一个根因**：上下文累积。

### 本方案四档降级

| 档 | 动作 | token |
|---|---|---|
| ① 抓取 + 去重 + 预筛 | 纯 Python 常驻脚本 | **0** |
| ② 无关通知（买教材 / 扫码入班） | 直接跳过 | **0** |
| ③ 规则可定位（`周X 第X节` / 地点明确） | 脚本直改真源 | **0** |
| ④ 自然语言说不清 | 唤起一次**全新短会话** | ≈ 3 万/次 |

**预估**：按实测通知频率（4 天 4 条，像日程变更的约 1–2 条/周）
→ **约 3–6 万 token/周**。对比「每 30 分钟轮询」每天数千万 → **省 3 个数量级**。

**关键设计**：起**新短会话、用完即弃** —— 不重发历史，顺便绕开「长对话卡顿」。
**绝不要**复用同一个长会话做轮询（那正是 Marvis #19 任务卡死 + 烧 token 的形态）。

### 完全零 token 的备选

只提示、不自动改：检测到新通知 → 在工作台显示「学习通有新通知，可能需要改日程」。
**不推荐** —— 与用户「一定要能实时写入、修改日程」的明示要求冲突，除非用户改口径。

## 🔌 让 Marvis 侧执行（机制实测 2026-09-23 19:45）

检测在我这边（0 token），改真源在 Marvis 侧。**Marvis 的任务机制：**

| 项 | 事实 |
|---|---|
| 任务存储 | **纯文件**：`%APPDATA%\Tencent\Marvis\User\<uid>\schedules\<id>_<n>_<m>.yaml`（数据库 15 张表里**没有**任务表） |
| ID 计数器 | `schedules\index`（内容 = 下一个 ID，本次实测 `19`） |
| 任务类型 | `interval`（每 N 分钟轮询）/ `timeout`（定点触发一次） |
| 状态字段 | `status: 0` = 停用 / `status: 1` = 启用（实测 #19 停用=0，#16/17 启用=1） |
| 执行记录 | `executed_list[]`，每次含 `time` / `conversation_id` / `status` |

### ★ 发现 1：每次执行 = 新会话（天生短会话，无需改造）

`19_0_0.yaml` 实测：`12:59 → conv_6e2ce279…` / `13:29 → conv_1a8bc017…` —— **两次执行两个不同会话**。
「短会话」本来就是它的形态，跑完即弃合理。

### ★ 发现 2：`timeout` 可当「立即执行一次」→ 事件驱动

`type: timeout` + `time_value: <现在+10秒>` = 让 Marvis **立刻起一个短会话**，仅一次。
→ 绕开 30 分钟轮询，空转为 0。

### ★ 发现 3：改 yaml 能被实时读到（间接实证）

#19 在 `13:53:28` 被改（停用）→ 此后**再无执行记录**（`executed_list` 停在 13:29）。
说明 agent **持续读取** schedules 目录，不是只在启动时读一次。

### ⚠️ 分工红线

**写 `schedules\` = 动 agent 内部文件 → 执行侧主场。**
规划侧只提供机制规格；落地由执行侧实现，或先确认这是官方支持路径。

## ✅ 「合理正确操作」六条保障（用户 2026-09-23 明示要求）

| 环节 | 保障 |
|---|---|
| 操作前 | 读真源原文 → 定位具体行 → **三锚点指纹校验**（`07:00 抢座` / `21:30 停屏` / `23:00 就寝` 三行逐字比对） |
| 判断 | 从通知提取「**日期 + 时段 + 内容**」三要素；**缺一个就不动** |
| 写入 | **单点替换**（只改目标行，绝不整段重写） |
| 操作后 | 回读校验 + **留修订记录**（改了什么 / 为什么 / 影响面 / 回滚点） |
| 幂等 | 按通知 `uuid` 去重，同一条处理两次不会重复写 |
| 失败 | **不写入 + 上报，绝不半改** |

> **核心原则：宁可不改，不可改错。**
